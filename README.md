# Secure Web-Based Student Complaint Management System (BUK) - version 2

A working prototype for Bayero University, Kano. Students submit complaints, each one is routed to the
office responsible, staff reply and update the status, and students follow every step.
Built with **Python, Flask and SQLite**. No separate database server is needed.

## 1. Installation (Windows, Linux or macOS)

1. Install Python 3.10 or newer (on Windows, tick "Add python.exe to PATH").
2. Open a terminal in this folder and run:

```
python -m venv venv
venv\Scripts\activate          (Windows)      source venv/bin/activate     (Linux / macOS)
pip install -r requirements.txt
python seed.py
python app.py
```

3. Open http://127.0.0.1:5000

`python seed.py` asks you to type a password for the administrator and each office. **Nothing you type is shown.**
Press Enter instead to have a strong password generated (it is printed once, and its owner must change it at first sign-in).

Other ways to run the setup script:
- `python seed.py --demo` creates sample accounts and sample complaints so every screen has something to show
- `python seed.py --generate` generates every password with no questions
- `python seed.py --set-password EMAIL` changes one person's password privately

### The BUK logo
Put the university logo in `static/img/` and name it `buk-logo.png` (or `buk-logo.jpg`).
It then replaces the placeholder everywhere: header, sign-in pages, landing page and receipts.

## 2. What is new in version 2

**Passwords:** eye button on every password field, live strength meter with a checklist, Caps Lock warning, match check,
forced password change at first sign-in for any account created by an administrator or generated by the system,
administrator password reset with a one-time temporary password, a generator button, and password rules
(10+ characters, three of four character types, common passwords refused).

**Two-step sign-in (optional, recommended for staff):** works with Google Authenticator, Microsoft Authenticator or Authy
(RFC 6238 codes), with 8 single-use backup codes, replay protection and lockout after repeated wrong codes.

**Complaints:** priority levels with response deadlines (urgent 24 h, high 48 h, normal 5 days, low 7 days) and overdue
flags, anonymous reporting (staff see "Anonymous student"), evidence upload (PNG, JPG, PDF, 2 MB each, encrypted,
checked by real content), follow-up messages, a status timeline and progress stepper, student confirm / reopen,
star rating after resolution, printable receipt.

**Staff:** dashboard with open, overdue and urgent counts, search, filters and sorting, quick replies,
internal notes the student cannot see, change priority, send to another office, escalation to the Dean, CSV export.

**Administrator:** analytics with charts (by category, status mix, 14-day trend, workload by office, resolution time,
satisfaction), account management (create, deactivate, unlock, reset password), searchable audit log with CSV export.
Administrators still cannot read complaint content.

**Design:** responsive layout, animations (page fade, card lift, counters, progress bars, toasts), dark mode,
accessible focus and keyboard use, reduced-motion support, session timeout warning with "Stay signed in".

**Notifications:** in-app bell with unread count for new assignments, replies, status changes and reassignment.
Notifications never contain complaint text.

## 3. Roles and routing

| Complaint category | Routed to |
|---|---|
| Hostel maintenance | Hostel management / maintenance officer |
| Security and harassment | University Security Unit officer only |
| Academic: course registration or other academic matter | Academic Affairs officer |
| Academic: examination result issue or records discrepancy | Examinations and Records officer |
| General student welfare | Dean of Student Affairs / Student Affairs officer |

Status flow: Submitted, Under Review, In Progress, Resolved, Closed. Each complaint gets a random reference such as `BUK-3F9A12CC`.

## 5. Security controls

- Salted password hashes (scrypt), lockout after 5 failed sign-ins, identical error for wrong password and unknown email.
- Optional two-step sign-in (TOTP) with encrypted secrets and hashed backup codes.
- Server-side access control on every request. A staff member can only open complaints assigned to their office; a direct
  link to another office's case returns "not found". Administrators cannot open complaints or evidence files.
- CSRF token on every form, secure session cookie, session renewed on sign-in, 30-minute idle timeout.
- Strict Content-Security-Policy with no inline scripts or styles, plus X-Frame-Options, nosniff, no-referrer, no-store, HSTS over HTTPS.
- Complaint titles, descriptions, replies, notes and evidence files are encrypted at rest. Reference numbers are random.
- Uploads are checked by their real content, size-limited, stored under random names and only served through an authorised route.
- Every query uses parameters (SQL injection) and every page escapes output (XSS). CSV exports are protected against formula injection.
- Audit log of sign-ins, failures, lockouts, submissions, staff views, status changes, replies, uploads, account changes and denied access.

## 6. Running the tests

```
python -m unittest -v
```
58 automated tests cover sign-in, lockout, two-step codes (including the RFC 6238 test vector), password rules, routing,
access control between every pair of roles, anonymity, evidence files, workflow, notifications, exports, encryption,
upgrade of older databases and audit logging.

## 7. Putting it online (HTTPS required)

Use `gunicorn "app:create_app()"` behind Nginx or Caddy with a free Let's Encrypt certificate, set `COOKIE_SECURE=1`,
set `SECRET_KEY` and `DATA_KEY` as environment variables, use `python seed.py --set-password` to give real passwords,
delete any demo accounts, and back up `instance/complaints.db`, `instance/uploads/` and the key files (keep the keys separate).
Without `data.key`, stored complaints cannot be decrypted.

## 8. Known limitations (state these honestly in the project)

- A student prototype. It has not had an independent security audit.
- No email or SMS sending. Notifications are inside the system only.
- Login and lockout counters are per account, not per network address, and there is no CAPTCHA.
- No integration with the university student database or single sign-on.
- Routing rules and office roles should be confirmed with BUK offices before real use.
